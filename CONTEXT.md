# Spensa

A meal planner and pantry tracker for one household (two people). You plan meals for the week, Spensa works out what's in the pantry and what to buy.

Stack: Vite + React + TypeScript, Mantine, TanStack Query, React Router, Supabase (Postgres + Auth + Realtime). Static SPA, mobile-first PWA. English UI only.

## Glossary

- **Household**: the unit that owns all data. A user belongs to exactly one household and joins it with an **invite code**. Every table is scoped to a household by RLS.
- **Ingredient**: a household catalog entry, named whatever the user likes ("pasta", "penne"). It has one **unit**: `g`, `ml`, `count` or `to_taste`. Optional fields: **category** (used to group the shopping list), **pack size** (for "≈ 1 pack" hints), **shelf life** in days (pre-fills expiry), **min stock** (makes it a **staple**).
- **To-taste ingredient**: unit `to_taste` (salt, oil). It has no quantity, only an **on hand / out** flag.
- **Recipe**: name, markdown instructions, optional tags, and **recipe ingredients**. Amounts are entered for a chosen **serves N** (1, 2, 3, 4, 6, 8; default 2) and stored **per portion**.
- **Slot**: a meal time in a day (default: lunch, dinner; configurable per household).
- **Planned meal**: date + slot + recipe + portions. A slot can hold several. A planned meal counts as **eaten on its date**, unless it is marked **didn't cook**. Past days can be edited.
- **Didn't cook**: `planned_meals.not_cooked`. The meal consumes no stock in the replay and never shows as short. Reversible.
- **Per-meal amounts**: a meal can have its own ingredient amounts (`planned_meal_lines`, a total per ingredient for that meal, to taste allowed). When a meal has any, they **replace** the recipe's lines for that meal in the replay and the shopping list, so a meal can use 300 g instead of the recipe's 200 g, add an ingredient the recipe lacks, or leave one out. No lines = follow the recipe. The recipe itself never changes.
- **Slot end time**: when a slot ends, per household (`households.slot_end_times`, keyed by slot name, edited in Settings). Defaults: lunch 14:00, dinner 21:30 (breakfast 10:00, snack 17:00, any other slot 21:30). It only decides when a check-in comes due.
- **Check-in**: "Cooked as planned?", asked 30 minutes after a slot ends, for each meal that day the replay found short (any shortfall). It is an **unread** item shared by the household: once either person answers (`planned`, `changed`, `not_cooked`, `dismissed`) it is cleared for both. It is created when due whether or not anyone has push on, has no expiry and no cap, and the number of unread ones is the app icon badge. "Done shopping" shows the unread ones one last time; anything left unanswered when the snapshot is saved counts as cooked as planned. Pushed (silent) to the meal's cook, or to everyone if it has none, once per meal. See [ADR 0005](docs/adr/0005-meal-check-ins.md).
- **Batch**: one purchase of an ingredient: quantity, date added, optional expiry. The pantry page lists a total per ingredient (batches as sub-lines) and edits batches in place once the pen icon enters edit mode.
- **Adjustment**: a manual stock change: `used X`, `set remaining to X`, `finished`, or `discard` (recorded as waste). Applies to the batch that expires soonest unless a batch is picked.
- **Snapshot**: the recorded remaining quantity of every batch at a moment. Saved by "Done shopping" at the end of a shopping trip. The Pantry page's "Save changes" writes no snapshot: it records only what changed, as adjustments (amount changed = `set`; removed = `finished` or `discard`, chosen from a menu) and new batches. A snapshot is the truth: events before it no longer change stock.
- **Soft delete**: nothing is ever hard-deleted. Deleting sets `deleted_at` and `deleted_by`; deleted rows are invisible to normal reads (RLS) and to the replay. **Restore** clears `deleted_at` (an undo), together with the children deleted with it. Every row also records `created_by`, `updated_by` (and their times), set by triggers and never by the client. See [ADR 0003](docs/adr/0003-soft-delete-and-authorship.md).
- **Replay**: how stock is computed. Start from the latest snapshot, then apply batches, planned meals and adjustments in date order. Meals use the batches that expire soonest first (FEFO). Nothing derived is stored. See [ADR 0001](docs/adr/0001-stock-by-replay.md).
- **Current stock**: the replay up to today. **Projected stock**: the replay including future planned meals.
- **Shortfall**: a planned meal needed more than the replay had. Stock never goes negative. The amount is used by the shopping list; the app does not show it as "short by X". Any shortfall on a meal whose slot has ended makes it a check-in candidate.
- **Expiring soon**: a batch that expires within the household threshold (`expiring_days`, default 3, editable in Settings).
- **Trip**: the current shopping trip, never stored as a record. Its range is today through the household **horizon** (`households.horizon_days`, default 7, 1 to 14), and it began after the last "Done shopping" snapshot. The only trip state is per planned meal: `planned_meals.skip_shopping` (default false). "Edit trip" on the Shop tab toggles it, it syncs like any other row, so both phones see the same list. A skipped meal is only left off the shopping list: it is still planned and eaten, so it still consumes stock in the replay. "Done shopping" clears every `skip_shopping`, starting a fresh trip. Items already in the cart stay there when meals are toggled.
- **Shopping list**: computed for the trip's range. For each ingredient, need = planned amount − stock usable on the meal's day (after earlier meals, excluding batches expired by then). It also includes staples below min stock, to-taste ingredients marked out, and **manual items** (free text, or an ingredient added by hand). **Ticking** an ingredient item creates a batch (a manual item is kept and marked bought, so unticking puts it back on the list as it was; bought items are cleared by "Done shopping"), with the quantity pre-filled as max(need, pack size) and expiry from shelf life. Ticks and trip changes sync live between phones (ticks are queued while offline). When the partner's change adds or removes still-to-buy items, the Shop tab shows one combined toast ("Anna changed the list: 2 added, 1 removed"); never for your own changes, and ticking an item off is not counted as removed.
- **Notifications**: web push to a person's installed devices (ADR 0004). **List-change push**: when the partner adds items to or removes items from the still-to-buy list, changes within 30 seconds arrive as one push ("Anna changed the list: 2 added, 1 removed", never to the author; bought items don't count as removed). **Expiry reminder**: one push a day at each person's chosen time (default 09:00, household timezone, or Off) listing batches with stock that expire within `expiry_reminder_days`. **Check-in push**: silent, about 30 minutes after a slot ends (see Check-in), with "Cooked as planned" and "Changed it" buttons on Android. Per person: list changes on/off, meal check-ins on/off and the reminder time (`push_prefs`). Per device: the push subscription (`push_subscriptions`), and "Not now" on the prompts for two weeks. On iPhone web push needs the app added to the Home Screen.
- **Settings**: shared by the household (on the `households` row, synced): shopping horizon, expiring-soon days (`expiring_days`), expiry reminder days (`expiry_reminder_days`, default 2), meal slots, slot end times (`slot_end_times`), timezone. Per device (localStorage only): theme, density, and which partner-ticked items you have acknowledged.

## Rules

- "Deleted" means soft-deleted and restorable. An ingredient can't be deleted while a recipe uses it. Its page lists those recipes.
- A recipe can't be deleted while a planned meal after the latest snapshot uses it. Its page lists those meals. Older meals keep pointing at the deleted recipe and show it as removed; restoring the recipe reconnects them.
- Quantities are decimals in the ingredient's unit. Metric only, no unit conversion.
